# Отчёт: слой управления фабулами

## Коротко

`ai.gena.services.fabula.manager` — библиотека поверх движка. В ней:

* реестр сценариев и версий с валидацией для редактора;
* теги (`trunk` и другие) с историей, откатом и A/B-аллокацией;
* индекс процессов как проекция журнала;
* дифф версий с подсказками маппинга;
* кампании миграции идущих фабул — анализ, кластеры, решения, безопасное применение
  и откат;
* разрешение конфликтов миграции доверенным агентом за портом;
* транспорт-независимое API из 52 операций с OpenAPI 3.1.

Тесты: 325 в слое менеджера и 679 в движке (из них 2 новых). Линтеры pyflakes и
pycodestyle чистые. Движок не менялся, кроме одного исправления ошибки (ниже).

## Сделано по запросу

| Запрос | Где и как |
|---|---|
| Слой управления фабулами, реализующими бизнес-требования | `Manager` в `service.py`. У сценария есть владельцы, метки и ссылки на требования (`ScenarioInfo.links`). |
| Дифф между версиями | `diff/` и `GET …/diff`: узлы, поля, дескрипторы, ключи контекста, текстовый дифф, `static_compat`, подсказки маппинга. |
| Найти фабулы, которые могут перейти на лету; переход опционален | Кампания анализирует каждую фабулу через `analyze_swap` и выдаёт вердикты `in_flight` / `with_restarts` / `blocked` / `busy` / `not_eligible`. Без решения никто не переезжает (`auto_apply_compatible` выключен). |
| Спрашивать пользователя; показать тех, кто не может перейти; выбрать способ разрешения | Кластеры с проблемами. Решения `migrate`, `resolve` (маппинг и миграция контекста), `stay`, `delegate_to_agent`, `cancel_fabula`. Уведомление `campaign.awaiting_decision`. |
| Автоматическое разрешение, где доверяем агентам, и API для них | `ResolutionPolicy` с режимами `manual`, `agent_proposes` и `agent_applies` и ограничениями. `/v1/agentic-resolutions`: аренда, бриф, dry-run, предложения, одобрение и отказ. Вызов агента закрыт портом `ConflictResolutionAgent`. |
| Оставить фабулы на их версии | Каждая фабула остаётся на своей версии (старой или новой), пока её не переведёт кампания: `stay` и решение по умолчанию, отмена кампании, `revert` для обратного перевода. |
| Перешивка trunk для тестирования новых версий | Теги с историей. Новая версия проверяется через явную версию или `canary`, не трогая `trunk`. |
| Откат к версии | `rollback` к ревизии или к версии. Для идущих фабул — `revert` кампании. |
| A/B в будущем, заложить в API | Аллокация с плечами и весами, детерминированный и липкий бакетинг, назначение в метках фабулы и в индексе, `GET …/tags/{tag}:resolve`. |
| Порты, где нужно | Хранилища, среда исполнения, каталоги, агент, права, id, уведомления (`ports/`). |
| API создания схем и информации о процессах для веба и других систем | 52 операции (`api/operations.py`), `dispatch` без транспорта, RFC 7807, `openapi.json`. |

## Тесты

* **Реестр**: идемпотентная публикация, конфликт содержимого, в том числе после
  изменения каталога; диагностика с позициями; устаревание версий; метаданные и
  политика с блокировкой.
* **Теги**: история и откат по ревизии и по версии, идемпотентность и блокировка,
  валидация аллокаций. A/B: детерминизм и липкость, доля плеча на 10 000 ключей в
  допуске. Назначение в метках и индексе. Перешивка спрашивает про идущие фабулы и
  никого не двигает.
* **Дифф**: таблицы изменений, переименование с подсказкой. Согласованность
  `static_compat` с `analyze_swap` на ожидающих фабулах для четырёх версий.
* **Индекс**:
  * совпадает с `host.view` после каждого шага и после падения хоста в каждой
    третьей точке `FaultInjector`;
  * сбой индекса не останавливает фабулу; разрыв версий помечает запись `stale`, и
    сверка её чинит;
  * старт, не дошедший до среды, становится `start_failed`, повтор запроса его
    перезапускает;
  * фабулы, стартовавшие мимо менеджера, и их импорт; фильтры, счётчики, пагинация.
* **Кампании**:
  * на лету с сохранением вызова, заморозка снимается;
  * кластеры и разрешение маппингом с перезапуском, упавшая фабула оживает;
  * подсказка переименования и откат;
  * `stay` освобождает фабулу для другой кампании;
  * фабула сдвинулась после одобрения → возврат к решению;
  * пауза оператора сохраняется;
  * `cancel_fabula`, `auto_apply_compatible`, идемпотентность, отмена кампании,
    пауза кампании, `refresh`;
  * падение менеджера до и после каждого из 7 вмешательств применения: каждая
    фабула переведена ровно один раз, ни одна не осталась на паузе.
* **Разрешение конфликтов**:
  * задачи по кластерам, содержимое брифа, `agent_proposes` с одобрением,
    `agent_applies`;
  * отказы по политике (действие, перезапуски, неприменимость, чужие фабулы, отмена
    вызова с эффектами);
  * аренда и её истечение, белый список;
  * отказ с возвратом задачи в пул и без него, устаревшее предложение;
  * раннер с `HintResolver`, упавший агент, закрытие задач при отмене кампании,
    разбор ответа LLM.
* **API**: сквозной прогон всех 52 операций через `dispatch` с JSON на входе и
  выходе. Ошибки как problem+json. Права по операциям. Маршрутизатор для каждой
  операции. OpenAPI совпадает с закоммиченным и замкнут по `$ref`.
* **Архитектура**: зависимости, порядок слоёв, `engine.testing` только в тестовом
  наборе, движок не знает о менеджере.

## Найдено ревью и исправлено

Независимое ревью слоя нашло 10 ошибок. Все воспроизведены, исправлены и закреплены
регрессионными тестами:

1. Отмена кампании после падения менеджера сразу за паузой-заморозкой оставляла фабулу
   на паузе навсегда.
2. Отмена после падения сразу за swap записывала уже переведённую фабулу как
   «оставшуюся».
3. Задачи разрешения конфликтов не закрывались, когда фабулы решали в обход агента, а
   повторное делегирование их дублировало.
4. `approve` и `submit` не выдерживали падения посреди применения. Теперь есть статус
   `applying`, и повтор доводит работу до конца.
5. `revert` терял тождественные пары маппинга (перезапуски) и маппинги отдельных
   фабул.
6. `revert` отказывал, если исходная версия устарела.
7. Повтор перешивки тега и повтор создания кампании возвращали успех, не доделав
   прерванную работу.
8. Исход вмешательства с id вида `mig:…:swap` нельзя было получить по HTTP-пути.
9. Некорректный тег в пути давал 500 вместо 400.
10. `failed_node` оставался в индексе после восстановления фабулы.

## Изменение в движке

При тестах кампаний нашлась ошибка: `Interpreter.analyze_swap` на завершённой или
отменённой фабуле падал с `KeyError`, потому что у неё нет корневого кадра.

* Теперь он возвращает неприменимый отчёт `not allowed while the fabula is …`, как и
  отказ `SwapVersion`.
* Добавлен тест в `engine/tests/core/test_fr10_swap.py` и строка в
  `engine/DESIGN.md` §8.

## Что не сделано и почему

* **HTTP-сервер.** В этом слое API без транспорта. Сервер на FastAPI сделан потом
  отдельным пакетом `ai.gena.services.fabula.server` (см. его `README.md`).
* **Реальные хранилища, шина уведомлений и LLM-клиент.** Есть только порты и
  реализации в памяти.
* **Адаптер к агентскому API tau** — это реализация порта `ConflictResolutionAgent`.
  Хелперы `agents/prompt.py` уже превращают бриф в промпт и разбирают ответ.
* **Черновики сценариев с ревизиями.** Пока черновик хранит клиент, а `:validate`
  проверяет текст.
* **Отложенный автоматический переход при выходе фабулы на совместимую точку.**
  Сейчас это ручной `:refresh`, после которого новые вердикты можно утвердить.
* **Аналитика A/B.** Назначение уже сохраняется в метках фабулы и в индексе.
* **Массовый импорт фабул, стартовавших мимо менеджера.** Движковый `FabulaStore`
  не умеет их перечислять; есть импорт по id и автоиндексация по первой версии
  журнала.

## Решения, принятые без спроса

Все 33 записаны в `DESIGN.md`, раздел 11. Главные:

* **Решения по умолчанию нет.** Фабулы остаются на своей версии; перешивка тега
  только открывает кампанию-вопрос.
* **Перед переводом фабулу замораживают паузой**, анализ повторяют и сверяют с
  одобренным. Каждое вмешательство отправляется, только пока его исход неизвестен.
* **`failed` фабулы — кандидаты миграции.**
* **Индекс — проекция журнала со строгим порядком версий.** Решения всегда
  принимаются по состоянию в среде исполнения.
* **Работать с задачами разрешения конфликтов** без белого списка может только актор
  вида `agent`. Отмена вызовов с неизвестными эффектами запрещена по умолчанию.

## Что понадобится для продакшна

* **Хранилища**:
  * реализации портов `ports/stores.py` в базе с условными записями по ревизии;
  * `FabulaIndex.query` с индексами по (сценарий, версия, статус, тег, плечо,
    `started_at`, `updated_at`) и меткам;
  * атомарные `TagStore.save` (состояние + история) и `CampaignStore.claim`.
* **Среда исполнения.** `FabulaRuntime` — эталонный `Host` или хост на движке класса
  Temporal. Хосту передаётся `service.journal_sink(...)`, а `ScenarioRepository` —
  это `RegistryScenarioRepository`. На асинхронной среде исход swap может появиться
  позже; кампания это выдерживает (элемент остаётся `applying`).
* **Фоновые задачи**: периодические `reconcile_stale`, `:refresh` открытых кампаний и
  `run_resolution_agent` для агентов внутри процесса.
* **HTTP**: аутентификация, которая даёт `Actor`, реализация `Authorizer` и маршрутизация
  через `Dispatcher.route`.
* **Уведомления**: `Notifier` в шину или вебхуки. События: `version.published`,
  `tag.moved`, `campaign.awaiting_decision`, `resolution.task_open`,
  `proposal.awaiting_approval`.
