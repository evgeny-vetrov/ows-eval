# Отчёт: движок интерпретатора сценариев Фабулы

## Коротко

Построена библиотека `ai.gena.services.fabula.engine`: слои `model`, `ports`, `dsl`,
`core`, `runtime` и тестовая обвязка `testing`. Дизайн, контракты, отклонения от OWS
и принятые решения — в `DESIGN.md`.

Тесты: 677 штук, все зелёные, весь прогон занимает около 6 секунд.

```
python -m pytest ai/gena/services/fabula/engine          # так прогонялось здесь
ya make -t ai/gena/services/fabula/engine                 # целевая команда
```

| каталог тестов | что проверяет | тестов |
|---|---|---|
| `tests/model` | фильтры событий, длительности, JSON-утилиты | 44 |
| `tests/ports` | `externalize`/`internalize`, тестовый вычислитель выражений | 42 |
| `tests/dsl` | парсер с позициями, валидатор профиля, компилятор графа | 69 |
| `tests/core` | сценарные тесты FR-2…FR-12, реплей, флаги семантики, совместимость, производительность, регрессии | 306 |
| `tests/runtime` | эталонный хост, пилот, падения на каждом шаге и повторные падения, конкуренция | 66 |
| `tests/architecture` | границы импортов, отсутствие часов и случайности в чистых слоях | 150 |

**Что не удалось проверить в этом окружении.**

* `ya` здесь нет, тесты гонялись pytest-ом. `ya.make` написаны по конвенциям Аркадии
  (`PY3_LIBRARY`, `PY3TEST` с `SIZE(SMALL)` в подпапках `tests/`), но не собирались.
  Пути `PEERDIR` (`contrib/python/pydantic/pydantic-2`, `contrib/python/PyYAML`,
  `contrib/python/jsonschema`) нужно сверить с деревом.
* Репозиторий был пустым: `ai/gena/services/theya/AGENTS.md` прочитать было нельзя, и
  `ai/gena/services/ya.make` не существовал. Родительский `ya.make` я создал с
  `RECURSE(fabula)`; в настоящем дереве это одна строка в существующем файле. Стиль
  взят из формулировок задания: идентификаторы и комментарии на английском,
  комментарии только о неочевидном, тесты проверяют поведение.
* Push в `origin` падает с 403: у сессии нет доступа к GitHub-репозиторию. Коммиты
  лежат в локальной ветке `claude/fabula-scenario-interpreter-i8ucj3`.

**Независимая проверка.** После написания код проверил отдельный агент-ревьюер:
чтение кода и фаззер на случайных сценариях и последовательностях стимулов.
Он нашёл 9 дефектов, все воспроизведены и исправлены, на каждый есть регрессионный
тест (`tests/core/cases_regressions.py` и строки в таблицах):

* `Goto` во время ожидания `schedule.after` запускал сценарий второй раз;
* восстановленный дедлайн составной задачи получал id уже сработавшего таймера;
* упавший скоуп не вычищал свою отложенную работу из агенды (после уступки по
  бюджету шагов);
* ретрай упавшей ветки `fork` с `compete` ронял ядро;
* стимул, отвергнутый из-за переполненной очереди паузы, нельзя было доставить
  повторно;
* смена версии с перезапуском на упавшей фабуле ничего не перезапускала;
* `then` на ветви `fork` молча игнорировался (теперь его отклоняет валидатор);
* терминальные уведомления хоста повторялись после падения без ключа
  идемпотентности (теперь у них есть версия перехода);
* экспоненциальный backoff переполнял `timedelta`.

После исправлений 3000 случайных сценариев прошли фаззер без падений ядра,
расхождений реплея и утечек операций.

## Сделано по требованиям

**FR-1. Разбор и валидация.** `dsl/parser.py` разбирает YAML и JSON по схеме YAML 1.2
core (`on:` — строка, даты — строки), ловит дубли ключей и alias-бомбы и строит карту
`JSON pointer → строка:колонка`. `dsl/compiler.py` за один проход валидирует профиль и
компилирует граф. Диагностика: код, сообщение, pointer, путь узла, строка, колонка. У
каждой запрещённой конструкции свой код: `forbidden.run`, `forbidden.use_extensions`,
`forbidden.use_authentications`, `forbidden.use_secrets`, `forbidden.secrets`,
`forbidden.schedule_every|cron|on`, `forbidden.call_http|grpc|openapi|asyncapi`,
`forbidden.use_functions|catalogs`, `schema.external`. Лимиты: 256 КБ, 300 узлов,
вложенность 10, 180 дней. Кубики и типы событий проверяются через каталоги, пути
фильтров — по схеме события. Работает без сети и хоста.
Тесты: `tests/dsl/test_validator.py`, `test_parser.py`, `test_compiler.py`.

**FR-2. Исполнение и поток данных.** Последовательность, `if`, `switch`, `then`
(`continue`/`exit`/`end`/имя), `set`, `raise`, выход с результатом, цепочка
`input.from → задача → output.as → export.as`, схемы входа и выхода задач и сценария.
Тесты: `tests/core/cases_flow.py`, `test_fr02_flow.py`.

**FR-3. Вызов кубиков.** `InvokeCapability` с детерминированным id, проверкой входа и
выхода по схемам из закреплённого дескриптора и подсказкой оставшегося времени.
Таймаут даёт `CancelInvocation` (если кубик отменяемый) и ошибку `timeout`. Результат
после таймаута или отмены → `StimulusIgnored(late)`. Встроенный ретрай дескриптора
делает новую попытку того же визита. Тесты: `cases_call.py`, `test_fr03_call.py`.

**FR-4. Таймеры.** `wait` на длительность (ISO, объект, выражение) и `{until: момент}`,
дедлайны задач (в том числе составных) и сценария, `schedule.after`.
Тесты: `cases_timers.py`, `test_fr04_timers.py`.

**FR-5. События.** `listen` выпускает по `Subscribe` на каждый фильтр: `with` плюс
вычисленная при входе корреляция, `since` = момент входа, `expires_at` = ближайший
дедлайн плюс запас. Реализованы `one`, `any`, `all`, `until` (выражение или событие),
`foreach` с буферизацией и `read`. Ядро само отписывается, отбрасывает дубли по
`delivery_key` и опоздания, перепроверяет фильтр через `EventMatcher`. Таймаут
`listen` ловится `try`. `emit` → `PublishEvent`. Тесты: `cases_events.py`,
`test_fr05_events.py`.

**FR-6. Ошибки.** RFC 7807 и стандартные типы OWS; `try/catch` с `errors.with`, `when`,
`exceptWhen`, `as`, `do`; `retry` с `limit.attempt.count`, `limit.attempt.duration`,
`limit.duration`, backoff `constant/linear/exponential` и детерминированным
джиттером. Необработанная ошибка → статус `failed` и команда `Failed`. Исключение
внутри ядра → `CoreError`, входное состояние не тронуто (тест с «взрывающимся»
портом). Тесты: `cases_errors.py`, `test_fr06_errors.py`.

**FR-7. Циклы.** `for` с `each`, `at`, `while`, выходом по `exit` и настраиваемым
потолком итераций. 10 000 итераций проходят меньше чем за секунду; при уступках
по бюджету шагов размер состояния между уступками не растёт.
Тесты: `cases_loops.py`, `test_fr07_loops.py`.

**FR-8. Параллельность.** `fork` с ветками и `compete`; проигравшие ветви закрываются
вместе с вызовами, таймерами и подписками; порядок детерминирован.
Тесты: `cases_fork.py`, `test_fr08_fork.py`.

**FR-9. Долгая жизнь.** Курсор — словарь кадров `путь → кадр` (явный стек, дерево из-за
`fork`), без рекурсии Python. Состояние ограничено: окна дедупа, очередь паузы и
буферы `listen` имеют потолки. На потоке из 300 событий размер состояния с какого-то
момента не меняется вовсе. Большие значения уходят в `BlobStore` через `externalize`;
каждый сценарный тест прогоняется ещё и с выгрузкой в блобы после каждого перехода.
Тесты: `test_fr09_long_life.py`, `test_replay.py`, `tests/ports/test_blobs.py`.

**FR-10. Вмешательства.** `Pause`/`Resume` (с накоплением стимулов и их применением
после возобновления), `Cancel`, `SkipTask`, `RetryTask`, `Goto`, `PatchContext`,
`CompleteWait`, `ExtendDeadline`, `SwapVersion`. Каждое действие проверяется на
допустимость, применяется целиком или отклоняется с кодом, идемпотентно по
`request_id` и журналируется с автором и причиной. `RetryTask`/`SkipTask`/`Goto`
возвращают к жизни упавшую фабулу, в том числе упавшую ветку `fork`.
`analyze_swap` показывает курсор, судьбу операций, перезапуски и недостающие
переменные, и этот предварительный отчёт совпадает с тем, что делает сама смена.
Тесты: `cases_control.py`, `test_fr10_control.py`, `cases_swap.py`, `test_fr10_swap.py`.

**FR-11. Отмена и завершение.** `check_case` для каждого сценарного теста проверяет,
что любая открытая операция либо закрыта командой, либо по-прежнему принадлежит
состоянию. `test_fr11_cleanup.py` отдельно покрывает каждый способ выйти из скоупа:
отмену, `compete`, `Goto`, `end`, ошибку ветви, дедлайн, смену версии, ретрай.

**FR-12. Наблюдаемость.** `core/journal.py` строит журнал шагов (узел, визит, попытка,
времена, вход, выход, ошибка) и текущие ожидания по наблюдениям,
`core/projection.py` — проекцию для API. Тесты: `test_fr12_observability.py`.

**FR-13. Эталонный хост.** `runtime/host.py`: загрузка (с досылкой неподтверждённого
outbox) → `apply` → сохранение с оптимистичной блокировкой вместе с outbox →
исполнение команд → журнал → подтверждение. Стимулы одной фабулы идут под
`asyncio.Lock`, конфликты между процессами разрешаются перечитыванием.

Пилот (`testing/pilot.py`: агент → PR вмёржен с корреляцией по id → `wait` 3 дня →
health check → утверждение человеком → комментарий в тикет) проходит в хосте в
памяти с фейковыми часами. Тест ломает хост на каждой из 50 точек (после загрузки,
применения, сохранения, каждой команды, журнала, подтверждения), перезапускает его и
доводит фабулу до конца. Каждый вызов исполняется ровно один раз, журнал совпадает с
прогоном без падения, если не считать записей о повторной доставке.
Тесты: `tests/runtime/test_host.py`.

**Нефункциональные требования.**
* Детерминизм и реплей — `test_replay.py`: каждый сценарный тест прогоняется
  подряд, с перезагрузкой состояния из JSON и свежим интерпретатором после каждого
  перехода, и с выгрузкой в блоб-хранилище; результаты совпадают побайтно.
* Идемпотентность по `stimulus_id`, `delivery_key`, `invocation_id` и `request_id` —
  тесты в FR-3, FR-5 и FR-10.
* Производительность: медиана перехода меньше 5 мс, 10 000 итераций быстрее секунды.
* Совместимость: `tests/core/state_v1_fixture.py` — замороженный JSON состояния схемы 1,
  который текущий код загружает и доводит до конца. Для будущих схем есть цепочка
  миграций в `core/codec.py`. У снимка сценария своя `schema_version`.
* Границы импортов — `tests/architecture/test_imports.py`.

## Что не сделано и почему

* **Настоящий jq.** По условию его нет; `testing/expressions.py` — явно тестовый
  вычислитель подмножества. Сверх заданного подмножества в нём есть `|`, `+ - * / %`,
  `//` и несколько фильтров (`length`, `keys`, `type`…): без них не написать счётчики
  и тесты циклов.
* **Предикаты кроме `eq` в `listen.with`.** Сам язык фильтров поддерживает все
  операторы (и тестами проверены все), но DSL выражает только равенство и
  корреляцию: иначе пришлось бы придумывать синтаксис, которого нет в OWS.
* **`use.functions`, `use.catalogs`, внешние схемы.** Отклоняются валидатором: кубики
  берутся только из платформенного каталога.
* **`poll` исполнителей.** Протокол `PollingCapabilityInvoker` описан, но хост не
  опрашивает исполнителей: в пилоте и тестах результаты приходят push-ом.
* **Сборка мусора в `BlobStore`.** Блобы адресуются по содержимому и не удаляются;
  когда их чистить, решает будущий хост.
* **Восстановление после дедлайна сценария.** После таймаута всего сценария у
  упавшей фабулы остаётся только корневой кадр, и вернуть её можно только через
  `Goto` на задачу верхнего уровня.

## Отклонения от OWS

Полный список — `DESIGN.md`, раздел 12. Главное: `call` — только кубики каталога;
`schedule` — только разовый `after` как задержка старта; `wait {until}`; `listen.with`
вычисляется при входе и переводится в фильтр `eq`; `correlate.expect` обязателен;
`until` вычисляется по каждому событию; `for` и `foreach` — свёртка; только
`evaluate.mode: strict`.

## Решения, принятые без спроса

Все 45 записаны в `DESIGN.md`, раздел 13, и закреплены тестами. Самые заметные:

* `fabula_id` — параметр `start`. Снимок сценария с закреплёнными дескрипторами
  хранится прямо в состоянии.
* Статус `failed` восстановим: цепочка упавших кадров сохраняется для `RetryTask`,
  `SkipTask` и `Goto`. Окончательны только `completed` и `cancelled`.
* Формулы backoff: `d`, `d·n`, `d·2^(n-1)`. Джиттер — sha256 от `fabula|path|n`.
  `limit.attempt.count` — число ретраев после первой попытки.
* `catch`, у которого есть `retry`, но нет `do`, после исчерпания ретраев ошибку
  пробрасывает.
* Выход `listen.to.all` упорядочен по объявлению фильтров. Это флаг семантики
  `listen_all_order`, на нём проверен сам механизм флагов.
* Дедуп стимулов — окном ограниченного размера плюс структурная проверка: к
  операции не в полёте стимул «опоздал».
* Длинные переходы уступают управление таймером `yield` с `fire_at = at`.

## Что понадобится хосту на движке долговременного исполнения (класса Temporal)

* **Где исполнять ядро.** `Interpreter.apply` можно вызывать прямо из кода workflow:
  он детерминирован и без ввода-вывода. Стимулы приходят сигналами или update-ами.
  Команды превращаются в активности (`InvokeCapability`, `Subscribe`, `Unsubscribe`,
  `PublishEvent`, `Cancel*`) и нативные таймеры (`StartTimer`/`CancelTimer`).
  Детерминированные id операций становятся id активностей и ключами идемпотентности.
* **Уступка.** Таймер `yield` с `fire_at = at` можно исполнять как немедленное
  продолжение, без реального таймера.
* **Continue-as-new.** Наблюдение `SafePoint` показывает точку, где агенда пуста.
  Состояние целиком в `FabulaState`. Большие значения нужно уносить `externalize` в
  блоб-хранилище до передачи в payload: лимиты payload у Temporal порядка мегабайт.
* **Ошибки ядра.** `CoreError` должна валить workflow task (движок повторит его), а
  не записываться в историю. Это же касается `ExpressionResourceExhausted` от адаптера
  jq со стенными часами.
* **Обновления движка.** Поведение, меняющее команды, включать только через флаги в
  `core/semantics.py`: фабула фиксирует их на старте, как patch/version-маркеры
  Temporal. `$runtime.version` берётся из зафиксированной версии.
* **API.** Query-обработчики отдают `project(state)`. Журнал собирается из наблюдений
  каждого перехода и пишется идемпотентно по `(fabula_id, version)` или по
  event id истории.
* **Права.** Проверку прав на вмешательства ядро не делает, это работа хоста.
  `request_id` должен быть стабильным ключом запроса.

## Что понадобится адаптеру к системе событий

* **Фильтр.** Перевести дерево `model.filter` один в один. Семантика должна совпадать
  с `testing/matcher.py`: предикат по отсутствующему атрибуту ложен (кроме `exists`),
  `matches` — поиск без якорей, `eq` различает `true` и `1`. Внешняя система может
  быть шире, но не уже: ядро перепроверяет и отбрасывает лишнее.
* **Подписка.** Upsert по `subscription_id`: повтор с более поздним `expires_at`
  продлевает подписку. Lookback с `since`. Доставка хотя бы один раз со стабильным
  `delivery_key` на пару (подписка, событие) и стабильным `stimulus_id` при повторе.
* **Маршрутизация.** По `subscription_id` адаптер должен найти фабулу: хранить
  соответствие или брать префикс id, до первого `/`.
* **Жизненный цикл.** Отписка по `Unsubscribe`, опоздавшие доставки после неё
  допустимы. После восстановления упавшей фабулы подписки приходят с новыми id
  (`~2`, `~3`) и прежним `since`.

## Что понадобится адаптеру к исполнителям

* **Вызов.** Идемпотентен по `invocation_id`. Результат приходит хотя бы один раз со
  стабильным `stimulus_id`. `cancel` — по возможности и тоже идемпотентен. Признак
  `cancellable` в каталоге честно говорит, умеет ли исполнитель отмену.
* **Контекст.** `InvokeCapability.context` (`run_as`, триггер, метки) передаётся как
  есть, для авторизации на стороне исполнителя. `timeout` — подсказка: дедлайн
  держит ядро.
* **Каталог.** Схемы входа и выхода, эффекты, таймаут и ретраи по умолчанию. Схемы
  проверяет ядро по дескриптору, закреплённому при публикации сценария, поэтому смена
  дескриптора в каталоге идущие фабулы не меняет.
* **Долгие операции** (например, человеческое утверждение) — обычный кубик с
  отложенным результатом. Если исполнитель не умеет push, адаптер реализует `poll`, а
  хост, который это понадобится, должен его опрашивать.
