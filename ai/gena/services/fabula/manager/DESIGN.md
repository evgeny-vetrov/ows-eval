# Слой управления фабулами — дизайн

Импорт: `ai.gena.services.fabula.manager`. Слой построен поверх движка
(`ai.gena.services.fabula.engine`); движок о нём не знает. Зависимости: стандартная
библиотека, pydantic v2, PyYAML, jsonschema и сам движок (проверяет
`tests/architecture`).

Задача слоя — продуктовое управление фабулами:

* реестр сценариев и версий;
* теги (`trunk` и другие), откаты и A/B;
* поиск процессов;
* дифф версий;
* перевод идущих фабул на новую версию — по решению человека или доверенного агента;
* API для веба и других систем.

## 1. Слои

```
model       домен и DTO (frozen pydantic): сценарии, версии, теги, записи фабул, дифф,
            кампании, политика разрешения, задачи, аудит, ошибки
ports       Protocol-ы с контрактами: хранилища, среда исполнения, каталоги, агент,
            права, id, уведомления
system      реализации системных портов без инфраструктуры (uuid, no-op уведомления)
deps        набор портов + кэш скомпилированных графов, аудит, уведомления
diff        чистый дифф двух версий
registry    реестр версий, валидация, публикация, теги, маршрутизация
fabulas     старт, индекс как проекция журнала, запросы, вмешательства, сверка
migrations  кампании миграции
resolution  разрешение конфликтов агентом: задачи, аренда, dry-run, политика
agents      хелперы вызова агента: промпт из брифа, разбор ответа, раннер
service     сборка всех сервисов (`Manager`) и `journal_sink` для хоста
api         фасад, таблица операций, dispatch без транспорта, OpenAPI 3.1
testing     реализации портов в памяти, стенд над engine.testing.World
```

Слой импортирует только себя и слои ниже. `engine.testing` доступен только в
`testing` и тестах. Всё сделанное — библиотека. HTTP-сервера, баз данных и
LLM-клиента в ней нет: они подключаются через порты.

## 2. Порты

| Порт | Назначение |
|---|---|
| `FabulaRuntime` | Подмножество `engine.runtime.Host`: `start`, `control`, `analyze_swap`, `swap_version`, `state`, `view`, `recover`. Эталонный `Host` подходит как есть; хост на движке класса Temporal реализует те же методы. |
| `ScenarioStore` | Сценарии (с ревизией) и иммутабельные версии. |
| `TagStore` | Состояние тега с ревизией и append-only история, пишутся атомарно. |
| `FabulaIndex` | Read-model фабул: insert/get/replace по ревизии, query с курсором, counts. |
| `JournalReader` | Чтение того, что хост записал в `JournalSink`. |
| `ControlOutcomes` | Долговечные исходы вмешательств по `(fabula_id, request_id)`. |
| `CampaignStore` | Кампании и их элементы (с ревизиями), `claim`/`release`: не больше одной активной кампании на фабулу. |
| `ResolutionTaskStore` | Задачи разрешения конфликтов. |
| `AuditLog` | Кто, что, когда, почему. |
| `CapabilityDirectory`, `EventDirectory` | Каталоги с `resolve` (подходит валидатору DSL) и `list` (для редактора). |
| `ConflictResolutionAgent` | Вызов агента, закрытый портом: `resolve(brief) -> proposal`. |
| `Authorizer`, `IdSource`, `Notifier` | Права, идентификаторы, уведомления веба и других систем. |

Хосту передаётся `service.journal_sink(inner, index, journal, outcomes)`. Это
`ManagerJournalSink`: после записи журнала он обновляет индекс и исходы вмешательств.
Хост находит версии по ref через `RegistryScenarioRepository`.

## 3. Реестр сценариев и версий

* **Сценарий** — `namespace/name`. У него есть заголовок, описание, владельцы, метки,
  ссылки на бизнес-требования и политика разрешения конфликтов.
* **Валидация** (`validate`) — диагностика движка с позициями (строка, колонка,
  указатель). Нужна живому редактору в вебе.
* **Публикация**:
  * текст проходит `load_scenario`, получается иммутабельная `ScenarioVersion`:
    исходный текст, снимок с закреплёнными дескрипторами, digest, автор, заметки;
  * ref и версия берутся из заголовка документа;
  * если `namespace/name` не совпадает со сценарием в пути, публикация отклоняется;
  * повтор с тем же digest — no-op;
  * другое содержимое под той же версией → `409 version_exists`. Digest включает
    дескрипторы каталога, поэтому после изменения каталога тот же текст тоже даёт
    конфликт, и сообщение это объясняет;
  * первая публикация создаёт сценарий (если его нет) и тег `trunk`.
* **Жизненный цикл**:
  * версии не удаляются;
  * `deprecate` запрещает новые старты и указатели тегов на версию. Для версии, на
    которую указывает тег, он отклоняется;
  * идущие фабулы и миграции по-прежнему находят устаревшую версию.

## 4. Теги, откат, A/B

* **Тег** принадлежит сценарию и хранит аллокацию — плечи
  `{arm, version, weight}`, веса в сумме дают 10000 б. п.:
  * одно плечо — обычный указатель на версию;
  * несколько плеч — эксперимент.
* **Операции**: `move`, `allocate`, `rollback` (к ревизии истории или к версии),
  `history`.
  * Каждая операция — новая ревизия, история append-only.
  * `expected_revision` включает оптимистичную блокировку. Без него запись
    последнего побеждает; чтобы создать тег, его не передают.
  * Повтор по тому же `request_id` — no-op.
* **Маршрутизация**:
  * `bucket = sha256(scenario|tag|salt|routing_key) mod 10000`, плечо выбирается по
    кумулятивным весам;
  * липкость гарантирована, пока не меняются аллокация и соль; смена соли означает
    новый эксперимент;
  * `routing_key` по умолчанию — id фабулы.
* **Назначение** (тег, ревизия, плечо, бакет, версия) пишется в `ExecutionContext.labels`
  с зарезервированным префиксом `fabula.` и в индекс. Оно едет вместе с состоянием
  фабулы и нужно будущей аналитике A/B.
* **Теги влияют только на новые старты.** При перешивке тега на одну версию
  (`move`, `rollback`) по умолчанию (`propose_migration=true`) открывается кампания
  миграции для идущих фабул этого тега на других версиях. Кампания только
  спрашивает: без решения ничего не переезжает.

## 5. Процессы

* **`start`**:
  * `fabula_id` по умолчанию — хеш `scenario + request_id`, поэтому повтор запроса
    ничего не стартует заново;
  * порядок: регистрация в индексе (`starting`, отпечаток запроса, метки,
    назначение) → `runtime.start`;
  * тот же `request_id` с другим телом → 409;
  * повторный старт использует уже сохранённое назначение, даже если тег успели
    перешить.
* **Индекс — проекция журнала** (`fabulas/indexing.py`):
  * `FabulaStarted` задаёт ref, статус `running` и время старта;
  * `StatusChanged` и `Waiting` задают статус и ожидания;
  * `SafePoint` — флаг «в покое»;
  * `ScenarioSwapped` меняет ref и добавляет запись в историю переходов;
  * `Fabula*` — терминальные статусы и последняя ошибка.

  Правила применения:
  * `StatusChanged` и `Waiting` приходят только при изменении, поэтому версии
    применяются строго по порядку. Хост пишет журнал на каждый переход, даже на
    пустой, так что пропуск виден;
  * версия не новее уже применённой — no-op; пропуск помечает запись `stale`;
  * ошибка индекса не валит flush хоста (иначе фабула застряла бы на
    неподтверждённом outbox) и тоже помечает запись `stale`.
* **Сверка** `reconcile`:
  * переигрывает журнал с последней применённой версии, пока версии идут подряд, и
    накладывает авторитетный `runtime.view`;
  * `reconcile_stale` чинит устаревшие записи и старты, не дошедшие до среды (через
    5 минут они становятся `start_failed`; повтор запроса перезапускает старт).
* **Фабулы, стартовавшие мимо менеджера**, попадают в индекс по первой версии
  журнала (`origin=external`). Если и её нет, есть `import` (`origin=imported`).
* **Запросы**:
  * фильтры: сценарий, версии, статусы, тег/плечо, метки, узел ожидания, даты
    старта, `stale`;
  * порядок по `started_at` или `updated_at` (по убыванию), курсорная пагинация;
  * `counts` по (сценарий, версия, статус).
* **Детали** — запись индекса плюс `runtime.view`. Журнал шагов собирается движковым
  `build_journal`.
* **Вмешательства** — все, кроме `SwapVersion`: версии меняются только кампаниями.
  * Ответ содержит исход из `ControlOutcomes`. Если исхода там нет, он ищется в
    журнале и дописывается в хранилище.
  * Окно `recent_controls` в состоянии для этого не годится: в нём 64 записи, и
    терминальные фабулы туда не пишут.

## 6. Дифф версий

Узлы сопоставляются по путям. Пути строятся из имён задач и переживают вставки и
перестановки.

* **Собственное определение узла** — его фрагмент документа, где каждый дочерний
  список задач заменён списком имён детей:
  * изменение внутри ребёнка видно на ребёнке;
  * добавление, удаление и перестановка детей видны на родителе;
  * дочерний список находится по общему правилу: указатель ребёнка —
    `<список>/<индекс>/<имя>`.
* **Состав диффа**:
  * `nodes` — added/removed/changed с полями, каждое с относительным указателем и
    старым и новым значениями;
  * `workflow` — корень без `/document/version`, добавленные и удалённые ключи
    `$context`;
  * `descriptors` — изменения закреплённых дескрипторов;
  * `text_diff` — unified diff исходников.
* **`static_compat`** — справочная статическая оценка:
  * проверяется только то, что сравнивает `engine/core/swap.py`: вид, скоуп,
    capability ref, фильтры `listen`, `fork.compete`;
  * удалённая ветка `fork` или удалённый `catch.do` дают `depends_on_state`;
  * авторитетен только `analyze_swap` каждой фабулы; согласованность проверяется
    тестом.
* **`mapping_hints`**:
  * удалённый узел сопоставляется с добавленным того же вида в том же скоупе;
  * баллы: 0.5 за вид и скоуп, +0.3 за тот же capability или фильтры, 1.0 при
    идентичном определении;
  * взаимно лучшие пары с баллом ≥ 0.8 и без соперников попадают в
    `suggested_mapping` — это маппинг кампании по умолчанию.

## 7. Кампании миграции

Кампания — «перевести фабулы сценария на версию X».

* **Кандидаты** берутся из индекса: версии, тег, статусы (по умолчанию `running`,
  `waiting`, `paused`, `failed`), явные id.
* **Клейм**: фабула участвует максимум в одной активной кампании. Занятые фабулы
  другой кампании видны как `not_eligible`.
* **Анализ** — `runtime.analyze_swap` по сохранённому состоянию с маппингом:
  подсказки диффа для исходной версии + маппинг кампании + переопределения элемента.
  Вердикты:
  * `in_flight` — перейдёт на лету, операции сохранятся;
  * `with_restarts` — перейдёт с перезапуском узлов и отменой операций;
  * `blocked` — неприменимо, `problems` объясняют почему;
  * `busy` — фабула не в покое (есть незавершённая работа);
  * `not_eligible` — завершена, отменена или уже на целевой версии.

  Упавшие (`failed`) фабулы переводить можно: это основной случай хотфикса, и
  перезапуск узла возвращает фабулу к жизни.
* **Кластеры** группируют элементы с одинаковыми (исходная версия, вердикт, курсор,
  проблемы). Веб показывает «N фабул стоят на `/ask`, сменился capability», и решение
  принимается сразу на кластер.
* **Решения** (цель — кластеры, id или вердикты):
  * `migrate` — утвердить текущий отчёт;
  * `resolve(mapping, context_migration, approve)` — переанализировать с новым
    маппингом и, если можно, утвердить;
  * `stay` — остаться на своей версии; это и поведение по умолчанию;
  * `delegate_to_agent` — передать конфликт агенту;
  * `cancel_fabula` — отменить фабулу.

  Повтор решения с тем же `request_id` — no-op.
* **`auto_apply_compatible`** (по умолчанию выключен) утверждает `in_flight` сразу;
  без него пользователя спрашивают о каждом кластере.
* **Статусы кампании**:
  * `awaiting_decision` — есть нерешённые или переданные агенту элементы;
  * `ready` — есть утверждённые;
  * `done`, `paused`, `cancelled`.
  * `cancel` оставляет все непереведённые фабулы на их версиях.
* **Применение** `apply` — по элементу, `n` — номер попытки:
  1. Если исход swap этой попытки уже записан или фабула уже на цели, элемент
     завершается без повторной отправки. Поэтому окно дедупа ядра (256 стимулов)
     не может привести к повторному применению.
  2. **Заморозка.** `running`/`waiting` фабула ставится на паузу
     (`mig:{c}:{f}:{n}:pause`), намерение сохраняется до отправки. Стимулы на паузе
     копятся в очереди ядра. Фабулу, которую поставил на паузу оператор, кампания
     не трогает и не снимает с паузы; `failed` сама не двигается.
  3. **Повторный анализ.** Он должен совпасть с утверждённым отчётом (курсор,
     операции, перезапуски). Иначе заморозка снимается, элемент возвращается к
     решению с новым отчётом, `n+1`.
  4. **Swap** (`…:swap`), исход — из `ControlOutcomes`. Если `ScenarioSwapped.report`
     разошёлся с утверждённым, элемент получает `diverged` (защитная проверка).
  5. **Снятие заморозки** (`…:resume`) — только если паузу ставила кампания.

  Каждое вмешательство отправляется, только пока его исход неизвестен. Состояние
  заморозки хранится, поэтому после падения менеджера на любом шаге повторный
  `apply` продолжает с того же места (проверено на каждом вызове, до и после).
* **Отмена кампании после падения менеджера.** Если исход swap уже записан, элемент
  засчитывается как переведённый. Если пауза-заморозка успела дойти до фабулы, фабула
  снимается с паузы.
* **`revert`** создаёт обычную кампанию обратно на исходную версию:
  * элементы группируются по (исходная версия, действовавший маппинг);
  * маппинг обращается целиком, вместе с тождественными парами, которые вызывали
    перезапуск;
  * цель может быть устаревшей версией;
  * `context_migration` не обращается: если нужна обратная миграция, её задают
    явно.
* **Повтор создания кампании** с тем же `request_id` доводит анализ до конца, если
  первая попытка прервалась.

## 8. Разрешение конфликтов агентом

«Агент» здесь — исполнитель, которому политика доверяет разрешать конфликты миграции.
Это не задачи фабул, которые вызывают агентов.

* **`ResolutionPolicy`** задаётся на сценарий, кампания может её переопределить.
  * Режимы: `manual` (делегирование запрещено), `agent_proposes` (агент предлагает,
    человек утверждает), `agent_applies`.
  * `allowed_actions` — по умолчанию `resolve` и `stay`.
  * `require_compatible` — только переходы без перезапусков.
  * `forbid_cancelling_effectful` (по умолчанию включено): нельзя отменять вызовы
    capability с эффектами, отличными от `none`; неизвестные эффекты считаются
    опасными.
  * `max_items`, белый список акторов (без него — любой актор вида `agent`),
    `expose_context_values`.
* **`AgenticResolutionTask`** — одна на кластер, крупные кластеры делятся по
  `max_items`.
  * Статусы: `open → leased → awaiting_approval → applying → applied`, плюс
    `rejected` и `closed`.
  * `applying` ставится до решений по элементам. Повторный `submit` или `approve`
    доводит прерванное применение до конца. При повторе `submit` под
    `agent_applies` применяется предложение, которое упавшая первая попытка успела
    сохранить.
  * Утверждённые отчёты перед применением ещё раз проверяются политикой.
  * Задача закрывается, когда ни одна её фабула больше ей не делегирована (решение
    приняли в обход агента). Повторное делегирование уже делегированных фабул
    пропускается.
  * Аренда с TTL; истёкшая аренда свободна, продлить можно повторной арендой тем же
    держателем.
* **Бриф** содержит:
  * курсор и ожидания фабулы-представителя, проблемы, недостающие ключи;
  * текущий и предложенный диффом маппинг;
  * фрагменты старых и новых определений затронутых узлов, узлы целевой версии;
  * разрешённые действия и политику;
  * JSON Schema ответа.

  Значения контекста в бриф попадают, только если политика это разрешает.
* **Путь предложения**:
  * `dry-run` не имеет эффектов;
  * `submit` снова делает dry-run и проверяет политику. При нарушении — 422 с
    нарушениями, аренда остаётся и можно попробовать снова. При успехе —
    `awaiting_approval` или сразу применение (`agent_applies`);
  * `approve` проверяет предложение ещё раз: устаревшее возвращает задачу в `open`;
  * `reject` возвращает задачу в пул или отдаёт элементы на решение человеку.
* **Аудит.** Каждое предложение, отказ и решение пишется в аудит вместе с
  обоснованием агента.
* **`agents/`** — хелперы для адаптера к агентской платформе (например, агентскому
  API tau):
  * `render_brief` превращает бриф в промпт, `parse_proposal` разбирает ответ;
  * `run_resolution_agent` — цикл `lease → agent.resolve → submit` поверх того же
    сервиса, которым пользуются внешние агенты.
* **`resolution/hint_resolver.py`** — детерминированный резолвер без LLM:
  подсказки диффа плюс перезапуск на месте.

## 9. API

* **`FabulaApi`** — по async-методу на операцию: `(actor, path, query, body)`.
* **`OPERATIONS`** — таблица 52 операций. Для каждой: метод, путь, модели запроса,
  query и ответа, право, группа, коды ошибок. Из неё строятся и `dispatch`, и
  OpenAPI.
* **`Dispatcher.dispatch`**:
  * принимает JSON-вход (query — строки или списки строк);
  * валидирует его моделями, проверяет право `Authorizer.allowed(actor, permission,
    resource)`;
  * вызывает фасад и возвращает статус и JSON;
  * ошибки превращаются в RFC 7807 с устойчивым `code` и расширениями
    (`diagnostics`, `dry_run`, `errors`).
  * `Dispatcher.route` сопоставляет метод и путь операции, поэтому HTTP-адаптер
    под любой фреймворк — несколько строк. Правила для `:` в пути — решение 31.
* **Соглашения**:
  * ресурсы `/v1/...`, пользовательские методы `ресурс:глагол` (`:apply`, `:move`);
  * мутации принимают `request_id`, изменения с блокировкой — `expected_revision`;
  * пагинация через `page_size` и `page_token`;
  * актор (`user | service | agent`) приходит из аутентификации транспорта.
* **Ошибки**: 400 — вход, 403 — права, 404, 409 — конфликт состояния, 412 —
  устаревшая ревизия, 422 — невалидный сценарий или нарушение политики.
* **OpenAPI 3.1** собирается из моделей (`api/openapi.py`). `openapi.json` лежит в
  пакете; тест сверяет его с генерацией и проверяет, что все ссылки разрешаются.

| Группа | Операции |
|---|---|
| scenarios | list/create/get/update, `:validate`, resolution-policy, versions (publish/list/get/`:deprecate`), diff |
| catalogs | capabilities, event-types |
| tags | list/get, `:move`, `:allocate`, `:rollback`, history, `:resolve` |
| fabulas | start, search, `:count`, `:reconcile`, get, journal, controls, controls/{request_id}, `:analyze-swap`, `:import` |
| migrations | create/list/get, items, clusters, decisions, `:apply`, `:refresh`, `:pause`, `:resume`, `:cancel`, `:revert` |
| agentic-resolutions | list, `:lease`, get, `:release`, `:dry-run`, proposals, `:approve`, `:reject` |
| audit | list |

## 10. Тестовый стенд

`testing.Stand` — это `engine.testing.World`, у которого хост читает версии из
реестра, а журнал пишет через `ManagerJournalSink`, плюс хранилища менеджера в
памяти.

* `WorldRuntime` исполняет мутации через `World.safely`: упавший хост пересоздаётся и
  восстанавливается.
* `testing.scenarios` содержит версии V1–V4 тестового сценария и `fleet` — фабулы в
  разных точках: на вызове, на событии, упавшая и завершённая.
* `CrashingRuntime` роняет менеджер до или после n-го вмешательства.

## 11. Решения

1. **Движок не меняется.** Единственное исключение — исправление ошибки
   `analyze_swap` на завершённой или отменённой фабуле: он падал с `KeyError`, теперь
   возвращает неприменимый отчёт с тем же текстом, что и отказ `SwapVersion`.
2. **Версия** — строка из заголовка документа; её формат не навязывается.
3. **`trunk`** создаётся первой публикацией; дальше теги перешиваются только явно.
4. **Тег без `expected_revision`** перезаписывается (запись последнего побеждает).
   Строгие клиенты передают ревизию.
5. **Липкость A/B** гарантирована только при неизменной аллокации и соли.
6. **Метки `fabula.*`** зарезервированы под назначение: метки копируются во все
   команды, и подделка назначения недопустима.
7. **`fabula_id` по умолчанию** — хеш сценария и `request_id`.
8. **Индекс** — проекция журнала со строгим порядком версий; среда исполнения
   авторитетна для всех решений.
9. **Ошибка индекса** не останавливает фабулу; запись помечается `stale`.
10. **Исходы вмешательств** хранятся отдельно от состояния, с запасным путём через
    журнал.
11. **Версии меняются только кампаниями**; в общих вмешательствах `SwapVersion` нет.
12. **Кандидаты кампании** по умолчанию включают `failed`.
13. **`busy`** определяется по непустой агенде состояния, а не по тексту проблемы.
14. **Кластер** — (исходная версия, вердикт, курсор, проблемы).
15. **Решения по умолчанию нет** — элемент остаётся на своей версии.
16. **Маппинг элемента** = подсказки диффа + маппинг кампании + переопределения
    `resolve`.
17. **Заморозка паузой** — всегда, кроме фабул на паузе оператора и `failed`.
18. **`request_id` вмешательств кампании** детерминированы: кампания, фабула,
    попытка, шаг.
19. **Каждое вмешательство** отправляется, только пока его исход неизвестен.
20. **Если исход swap ещё не виден** (асинхронная среда), элемент остаётся
    `applying`, а следующий `apply` продолжит.
21. **`revert`** обращает только переименования; миграцию контекста задают явно.
22. **Отмена кампании** снимает заморозки, закрывает задачи и оставляет фабулы на
    месте.
23. **Одна задача на кластер**; крупные кластеры делятся по `max_items`.
24. **Работать с задачами** без белого списка могут только акторы вида `agent`.
25. **Неизвестные эффекты capability** считаются опасными.
26. **Отклонённое по политике предложение** не меняет задачу (агент может повторить)
    и пишется в аудит.
27. **`approve`** перепроверяет предложение; устаревшее возвращает задачу в пул.
28. **Права проверяются на границе API**; сервисы внутри процесса доверяют
    вызывающему. Доменные правила политики разрешения проверяются всегда.
29. **Ошибки API** — RFC 7807 с `type = urn:fabula:problem:<code>`.
30. **HTTP-обвязки, баз данных и LLM-клиента в пакете нет** — только порты и
    реализации в памяти.
31. **Параметр пути не содержит `:`** (с него начинается пользовательский глагол).
    Исключение — завершающий `{request_id}`, потому что менеджер сам порождает id вида
    `mig:<кампания>:<фабула>:<попытка>:swap`. Маршруты с глаголом проверяются первыми.
    `request_id` не содержит `/`.
32. **Повтор перешивки тега** (тот же `request_id`) снова вызывает предложение
    кампании. Кампания идемпотентна, так что прерванная первая попытка не остаётся без
    вопроса пользователю.
33. **`failed_node` в индексе сбрасывается**, когда фабула выходит из статуса
    `failed`.
